## Publish only after review and green integrated CI

Run from an authenticated clone. Check that PRs #29 and #30 and the release-preparation PR are merged into `main`, and the latest CI run is successful:

```bash
git switch main
git pull --ff-only
git fetch origin --tags
test "$(node -p "require('./package.json').version")" = "0.4.0"
test -z "$(git status --porcelain)"
test -z "$(git tag --list v0.4.0)"
pnpm install --frozen-lockfile
composer validate --no-check-publish
composer install --no-interaction
pnpm check
composer run syntax
pnpm package
node scripts/validate-release.mjs
git tag v0.4.0
git push origin v0.4.0
```

Confirm the **Release** workflow succeeds and GitHub marks v0.4.0 as a **prerelease**, not latest stable. Inspect its five assets. A green PR packaging artefact is not the published candidate.

## Staging native-update test

Use the permanent starter staging installation at https://gd.ezhostforall.com/. Record its actual installed versions before proceeding; the previous successful test reported all three at 0.3.0, but inspect the current host rather than assuming.

1. Back up the database/uploads/files and retain verified 0.3.0 ZIPs. Preserve the working private configuration, credentials, salts, table prefix and host-specific HTTPS/cookie settings.
2. Keep all three installed components on the older 0.3.0 versions for the first native discovery test. Confirm `WP_ENVIRONMENT_TYPE` is `staging`.
3. In the existing `EZHOST_UPDATE_SOURCES` array, change the intended component entries' old `candidate_tag` values to **`v0.4.0`**. Do not create a second constant or replace the entire wp-config. Keep their repository and server-side read-only token unchanged.
4. Open WordPress Admin → Dashboard → Updates and refresh normal update checks. Allow for WordPress caching and the updater's 15-minute metadata cache. All three 0.3.0 → 0.4.0 updates should be offered for the allowlisted IDs.
5. Install through the native screen and verify the theme/plugin directory names and versions. Confirm the updater remains active, its hooks are registered and another update check completes normally.
6. Preview existing pages, header/footer, cards, buttons, optional React/animation and content without JavaScript. Compare default colours, spacing and widths with the previous version. The known desktop menu-toggle issue is tracked separately in #15; do not attribute it to tokens without a before/after check.
7. Open and save representative block content in staging. Compare palette, body fonts, spacing controls, narrow/wide blocks and any saved global-style overrides with the frontend. Check 320px and desktop, keyboard focus and contrast; avoid overwriting approved client content.
8. Review PHP/browser errors, optional plugin absence and any enabled sandbox integration routes. Do not send real leads or production deliveries from this test.
9. Restore the known-good 0.3.0 packages to rehearse rollback. Check frontend/admin and then reinstall the same 0.4.0 candidate through native updates. Record both results. No database schema change is included; retain backups regardless.
10. Run the read-only **Staging smoke test** workflow after installation. Its success supplements the manual checks and does not prove installation, editor usability or rollback.

Client repositories created by the initialiser must use their own update sources and independent staging; do not apply this starter allowlist to a client site.
