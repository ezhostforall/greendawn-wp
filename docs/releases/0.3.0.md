# Candidate v0.3.0 — staging update smoke test

**Historical status:** v0.3.0 has been published and promoted to approved stable. The original first-candidate walkthrough below is retained as history; do not republish this tag. Use the [v0.4.0 checklist](0.4.0.md) for the next candidate.

## Scope

- Synchronise package, WordPress theme and both plugin versions from `0.2.0` to `0.3.0`.
- Add a sanitised `wp-config.example.php` for secure staging setup and staging-only candidate selection.
- Ignore real `wp-config.php` files; include example syntax checks and lightweight tests for accidental candidate enablement or forgotten secret placeholders.
- Document the exact private GitHub candidate update test.

No new frontend features or client business logic are intentionally included. This is a controlled end-to-end test of release discovery, checksum verification, WordPress ZIP installation and rollback.

## Test environment

- Persistent staging: https://gd.ezhostforall.com/
- Baseline: installed theme and plugins version `0.2.0` (verify individual plugin versions before starting).
- WordPress must report `WP_ENVIRONMENT_TYPE=staging`.
- `EZHOST_UPDATE_SOURCES` must allowlist the private `ezhostforall/greendawn-wp` repository, with an appropriate read-only GitHub token stored **only** on the hosting server.
- Do not overwrite the existing site's `wp-config.php` with the template. Preserve its existing database connection, salts and table prefix.

## Publish after PR approval and merge

In a Codespace on the merged `main`:

```bash
git checkout main
git pull --ff-only
pnpm install --frozen-lockfile
composer install --no-interaction
pnpm check
pnpm package
node scripts/validate-release.mjs
test "$(node -p "require('./package.json').version")" = "0.3.0"
git tag v0.3.0
git push origin v0.3.0
```

Check the `Release` GitHub Actions run and verify that `v0.3.0` is a **prerelease** containing all three component ZIPs, `updates.json` and `checksums.sha256`.

## Test native update on staging

1. Back up staging (database, `wp-content` and the current ZIPs).
2. On the staging server only, add `'candidate_tag' => 'v0.3.0'` to each intended component entry in the existing `EZHOST_UPDATE_SOURCES` configuration. Do not add a second definition of the constant. The example template shows these lines commented out.
3. WordPress Admin → Dashboard → Updates → Check again. Allow for the plugin's 15-minute release metadata cache and WordPress update transients.
4. Verify `0.2.0 → 0.3.0` is offered for Greendawn, Greendawn Core and EZ Host Updater; install the updates through the native dashboard.
5. Verify the new versions, homepage, styles, React example if present, navigation, WordPress editor, PHP errors and Plugins page. Run the read-only staging smoke workflow after confirming its environment variable `WP_STAGING_URL` is correct.
6. Practice reverting the installed ZIPs if necessary and confirm the site still works.
7. Record staging acceptance. Only then run **Actions → Promote tested release** for `v0.3.0` with `staging_verified` checked.

Do not use any CI test administrator credentials on staging. The release promotion changes the visibility of the same validated assets; it does not rebuild ZIPs or deploy automatically.
